# Единый сценарий / Unified scenario

## Визуальный контракт

Эталон — единый интерфейс `simulation.html` и его обзор / раскрытая стойка.
Сохраняем сцену 1920×1080, масштабирование целиком, тёмный фон с сеткой, кремовую
типографику, coral-веса, mint-KV, amber-нагрузку. GPU — физически узнаваемые
карты с радиаторами и шардами весов. Drill-down внутри текущего сценария.
Новая страница использует локальные шрифты (Manrope/Avenir Next/Arial), без CDN.
Скриншоты версии: `docs/screenshot-unified.png`, `docs/screenshot-unified-rack.png`.

## Вход и пользовательский путь

`distr/index.html` и `distr/simulation.html` — одинаковая страница из исходника
`simulation.html`. Соседние `sim-core.js` и `scenario-core.js` обязательны, в том
числе при открытии через file://. Устаревшие самостоятельные калькуляторы удалены; оба уровня доступны здесь.

Пример / ручная равномерная нагрузка / CSV → профиль модели → GPU, карты и
реплики → проверка памяти → расчёт → воспроизведение / раскрытие стойки →
сравнение с вариантом A → CSV результатов или JSON сценария.

Пример — живой трейс OpenClaw из `examples/trip-moscow-nizhny/requests-live.csv`:
По умолчанию 100 000 пользователей, одна задача на пользователя за 24 часа,
равномерный приход. Каждая задача повторяет 6 вызовов с исходными смещениями.
Поля `users`, `tasksPerUser`, `periodHours` задают объём и средний вход;
`profile`, `hourWeights` — распределение по времени. Детальная симуляция ограничена
окном и 1666 задачами; правила описаны в разделе «Нагрузка за период» ниже.
После редактирования нужен пересчёт; сравнение A сбрасывается.
Ручной поток и CSV не умножаются на число пользователей, поля в этих режимах отключены.
На задачу — 28 200 входных / 2 400 выходных токенов; итог от провайдера,
разбивка по вызовам реконструирована (`live_run_reconstructed`). `job_id` различает
задачи; `depends_on` сохраняется как метаданные и не управляет исполнением.
Это повтор внешнего расписания, не DAG-модель пользовательских операций.

При открытии пример уже рассчитан; воспроизведение на паузе на 18% времени.
На схеме — момент времени, в нижнем ряду — весь прогон. Изменение настроек
сбрасывает результат до явного пересчёта. Новая нагрузка сбрасывает вариант A.
Воспроизведение не меняет расчёт: читает события готового расписания.
Открытие стойки сохраняет воспроизведение; внутри доступны синхронные
play/pause, ползунок времени и скорость. Перетаскивание любого ползунка
ставит воспроизведение на паузу. Возврат сохраняет выбранный момент.
На каждой реплике видны занятый и свободный KV-бюджет, индикатор доли
занятого бюджета; в компактной раскладке остаётся свободный объём.
Цифры обновляются при старте/завершении запросов, а не растут по токенам.
В стойке свободная память карты показана до сотых ГБ. Индикаторы используют
линейный масштаб без искусственного увеличения малых значений.

## Контракт расчёта

- Внешний заданный поток, строгая FIFO-очередь, 1–64 реплик; на каждой
  1–256 одновременно активных запросов. Следующий запрос назначается реплике
  с наименьшим числом активных запросов среди тех, где есть слот и память.
  Большой головной запрос не обходится меньшим запросом.
- Скорости prefill и decode — одиночные скорости **на всей реплике**, не на GPU.
  Количество карт не экстраполирует их автоматически. Профили учебные.
- Для n активных запросов общий выигрыш G(n) = 1 + (n−1) × gain.
  Каждый запрос получает G(n)/n от своей одиночной скорости. Prefill и decode
  делят один нормированный бюджет; смена состава немедленно меняет скорости.
  gain=0 — постоянная общая производительность, gain=1 — идеальное линейное
  масштабирование. В UI gain задаётся в процентах; по умолчанию 50% и 8 слотов.
  Это **иллюстративное допущение, не измерение batching на GPU**.
- События: поступление, конец prefill, первый токен, завершение.
  TTFT = фактический момент первого токена − arrival, включая очередь и sharing.
  Snapshot использует полуоткрытые интервалы; проигрывание не меняет расчёт.
- KV на запрос = (input+output) × 2 × layers × kvHeads × headDim × 2 / 1e9 ГБ.
  Полный резерв выделяется при старте и освобождается при завершении.
  Очередь KV не занимает. Рост кэша по токенам и prefix caching не моделируются.
- На реплике: KV budget = cards × GPU memory − FP8 weights − runtime reserve.
  Все активные запросы должны суммарно помещаться в бюджет. Нехватка места
  оставляет запрос в очереди; если хотя бы один запрос не помещается отдельно
  или превышает контекст модели, прогон блокируется. Допуск округления — 1 байт.
- «По памяти» = floor(KV budget / KV самого длинного запроса): консервативное
  количество одинаковых максимальных контекстов, не ограничение на число
  пользователей. Более коротких запросов может поместиться больше.
- Оценка пропускной способности при полной загрузке = replicas × G(n) /
  mean(input/prefill + output/decode), где n = min(слоты, оценка по памяти).
  Это ориентир по среднему составу нагрузки, не измеренный throughput прогона
  и не гарантия задержки. Для неоднородных запросов реальный состав меняется.
- Причина ожидания в выбранный момент: если все слоты заняты — лимит
  параллельности; при наличии слотов — память для головного запроса.
  Диагностика объясняет admission в этой модели, не аппаратный bottleneck GPU.
- Полная аренда = replicas × cards × USD/GPU/hour × duration_hours, от t=0
  до последнего завершения, включая простой. Не месячная экономика.
- В drill-down и мини-картах KV — сумма резервов активных запросов в выбранный
  момент. При простое KV=0; веса и резерв среды остаются.

Модель сохраняет стиль стойки, но не эмулирует vLLM: нет chunked prefill,
preemption, отдельных prefill/decode бюджетов и реальной кривой аппаратной
производительности. gain в этой версии остаётся пользовательским допущением.

## Профиль B300

В выборе оборудования доступен B300 с 288 ГБ номинальной памяти на GPU.
Источник: [NVIDIA DGX B300 User Guide](https://docs.nvidia.com/dgx/dgxb300-user-guide/introduction-to-dgxb300.html), проверено 2026-10-14.
Существующие формулы памяти используют этот объём и заданный резерв среды.
Стартовые скорости (множитель 1,4 к профилю модели) и цена 5 USD/GPU/hour
унаследованы от сценарного B200; это не замер B300 и не коммерческий тариф.
Интерфейс явно подписывает происхождение начальных значений. Дополнительная
память не меняет заданную скорость автоматически. URL и JSON используют ключ B300.

## Форматы

CSV: `request_id,arrival_ms,input_tokens,output_tokens`, 1–10 000 строк,
до 2 MiB. Уникальные непустые ID; целые числа от 0 до 1e9, output ≥ 1.
Пустые числовые ячейки запрещены. Простой comma-parser: без quoted/multiline.
Дополнительные колонки сохраняются, но не изменяют исполнение. DAG и смешанные
модели не поддержаны. Файлы не отправляются на сервер.

JSON: `schema_version=sm-gpu-calc/2`, `core_version=0.3.0`,
`profile_version=educational-2026-09-28`, `workload`, `settings`, опционально
`result`. До 8 MiB при импорте. Результат пересчитывается; сохранённым цифрам
не доверяем. Старый формат /1 с core 0.2.0 мигрирует в concurrency=1, batchGain=0,
сохраняя последовательную семантику; остальные несовместимые версии отклоняются. Экспорт хранит метаданные входа.
Опциональный `workload_source` с `type:'openclaw-period/1'` хранит параметры
периода и окна (см. ниже). Прежний `type:'openclaw-live/1'` с `users` и
`usersPerSecond` также поддерживается и сохраняет полный исходный трейс. Импорт проверяет совпадение с шестишаговым трейсом по ID,
arrival, токенам и метаданным происхождения; несовпадение отклоняется. Дополнительные
поля строк сохраняются при импорте и пересчёте. Старые /2 без workload_source
открываются как фиксированный трейс без управления пользователями.

URL без данных: `lang`, `model`, `gpu`, `replicas`, `cards`, `prefill`, `decode`,
`price`, `reserve`, `concurrency`, `batchGain`, `users`, `tasksPerUser`,
`periodHours`, `profile`, `hourWeights`, `windowMinutes`; для проверки
`progress=0..1` и `drill=1`. Прежний `usersPerSecond` поддерживается, если нет `periodHours`.
Пример: `simulation.html?lang=en&replicas=4&cards=8&progress=0.5`.

## Пользователи и RPS

- Пик входящего потока — максимум числа arrival в любом полуоткрытом окне 1000 мс.
  Одновременные приходы считаются раздельно; два прихода с разницей ровно 1000 мс
  не входят в одно окно. Это показатель всего входа, не текущего кадра.
- Средний вход за период = 6 × users × tasksPerUser / (periodHours × 3600).
  Профильный пик — среднее за самый нагруженный час, а не секундный пик трейса.
  Для прежнего режима openclaw-live/1 длительный вход = 6 × usersPerSecond.
- Оценка saturation не изменена: replicaRps=G(n)/mean(input/prefill+output/decode),
  poolRps=replicas × replicaRps. Это не измеренный предел и не гарантия задержек.
- Доля длительного входа от этой оценки не равна GPU utilization.
- Средний выход прогона = completed / duration_seconds, включая простой и хвост.
- Карты реплики совместно обрабатывают вызов: RPS реплики не делится на cards.

## Ограничения текущей версии

Нет калибровки по аппаратным бенчмаркам, DAG/closed-loop, аппаратно калиброванного
batching, interconnect, сравнения с API pay-per-token, CLI/MCP и автоматического
выбора GPU под SLA. Для локального запуска нужны HTML и оба файла ядра рядом.

## Поставка

`bash scripts/release.sh` добавляет SHA-256 версии в URL обоих JS-файлов,
синхронизирует index и simulation, запускает тесты и
рендер, проверяет совпадение исходников, создаёт ZIP по явному списку файлов.
Незакоммиченная сборка маркируется `dirty`. Ничего не публикуется автоматически.
Перед загрузкой ZIP через серверный deploy.php нужно осмотреть скриншоты;
сам deploy.php в этом репозитории отсутствует. Локальные инструкции и трейсы
не включаются в архив. Загрузка на mikhaylov.com выполняется отдельно от сборки.

## Проверка этой версии

37 Node-тестов (включая живой CSV, масштабирование, RPS и параметры JSON): FIFO, баланс, совместное исполнение, смешанный prefill/decode,
изменение скорости при поступлении/завершении, реальный TTFT, KV admission и
освобождение, точная граница памяти, цена, CSV/JSON и миграция /1 → /2.
Независимое ревью ядра выполнено; исправлено расхождение округления между
preflight и admission. Стресс 10 000 запросов занимает около 1,5 с локально;
расчёт синхронный, на пределе интерфейс может кратко приостановиться.

Контрольный сценарий: 24 запроса через 200 мс, 10 000 входных + 1000 выходных,
2 реплики по 8 B200, GLM-5.3, prefill 2800, decode 84, резерв 10%.
Один слот → 185,91 с, peak queue 22. Восемь слотов при gain=50% → 53,43 с,
peak queue 8; полный batch резервирует 32,44 ГБ KV на реплике. Эти результаты
зависят от учебных допущений, не являются бенчмарком B200.

Браузерная проверка: ручная нагрузка, сравнение 1/8 слотов, ограничение памяти
при резерве 50% (4 активных на реплике), KV=0 после завершения, невозможное
размещение, справка о sharing, импорт JSON /1 (185,91 с) и /2 (53,43 с),
RU/EN, восемь реплик и стойки на 8/16 карт. CSV-выгрузка теперь включает
first_token_ms. Формат экспорта проверяется через core round-trip; получение
скачанного файла во встроенном браузере не подтверждено.

Проверка live KV: ползунки обоих уровней, непрерывное воспроизведение при
открытии стойки, автоостановка в конце, освобождение KV до нуля, отсутствие
ошибок JS, RU/EN, компактные карточки восьми реплик.

Статический хостинг может кэшировать JS надолго. HTML с неизменным
`src="sim-core.js"` способен загрузить старое ядро после обновления HTML.
Поставка использует `sim-core.js?v=<hash>` и `scenario-core.js?v=<hash>`;
версии детерминированы содержимым, обновляются release-скриптом. При изменении
JS пересоберите и загрузите весь ZIP, включая index.html и simulation.html.

## Большой пул реплик

9–64 реплики отображаются компактной матрицей, до 40 на странице. Каждая ячейка —
одна реплика: номер, активные запросы / лимит, цвет фазы и доля занятого KV.
Сводка активности и KV относится ко всему пулу, включая другие страницы.
Клик открывает карты выбранной реплики; страницы не меняют расчёт и время.
До 8 реплик сохраняются подробные карточки. Формулы и допуск по KV не изменены.

## Нагрузка за период и ограниченный прогон

`openclaw-period/1`: users (1–10⁷), tasksPerUser (целое 1–100), periodHours
(от 1 мс до 168 ч), profile (uniform/hourly), windowMinutes (1–60), hourWeights
(24 числа 0–1000, сумма > 0). Hourly требует periodHours=24.

N = users × tasksPerUser; всего 6N вызовов, 28200N входных и 2400N выходных токенов.
Средний RPS = 6N / (3600 × periodHours). Для hourly:
RPS часа h = 6N × weight[h] / sum(weights) / 3600; пик — максимум этих средних.
Для uniform пик профиля равен среднему. Это не дискретный пик прихода за секунду.

Задачи начинают исполняться по детерминированным квантилям k/N накопленного
профиля (k=0..N−1). Повторные задачи распределяются независимо, без сессий.
Симулируемое окно начинается с первого часа максимального веса; uniform — с 0.
Окно полуоткрытое, включает старты задач; 6 вызовов и хвост каждой включённой
задачи сохраняются. Максимум 1666 задач: конец окна сокращается до старта
следующей задачи. Округление arrival до миллисекунд — как в обычном ядре.

Время внутри прогона относительное к началу окна. Перед ним очередь пуста;
предыдущие часы и их хвост не моделируются. p95, peakQueued, длительность и
аренда не экстраполируются на период. Расчёт показателей потребности за период
не требует генерации всех вызовов. Скорости/G(n)/планировщик не изменены.

JSON сохраняет полный workload_source и фактический workload фрагмента. При
импорте проверяется точное совпадение с генератором; дополнительные поля сохраняются.
Старый openclaw-live/1 читает исходный полный трейс. URL: users, tasksPerUser,
periodHours, profile, windowMinutes, hourWeights (24 числа через запятую).
usersPerSecond совместим: без periodHours период = users / usersPerSecond / 3600.
