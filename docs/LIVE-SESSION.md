# Live session API (experimental)

The root `SimCore` now has a single deterministic event engine for finite and
incremental execution. `simulate(workload, config)` keeps its existing result
shape and serving rules. This source change is experimental and has not been
published to the hosted calculator. `distr/` is not synchronized in this step.

## Core

```js
const session = SimCore.createSession(config);
session.enqueue(requests);             // same validated rows as simulate
session.advanceTo(500);                // absolute model milliseconds
session.enqueue(newFutureRequests);    // arrivals at or after current time
const state = session.inspect();
const restored = SimCore.restoreSession(JSON.parse(JSON.stringify(session.save())));
```

- `advanceTo(t)` is monotonic. Observation does not split service integration
  steps; different frame frequencies give identical event times.
- `enqueue(rows)` is atomic on validation failures. Known future arrivals are
  ordered by time and request ID; separate submissions at the same current
  instant are ordered by the submission actions. Already admitted work is never
  reordered by a later submission.
- KV, FIFO, normalized prefill/decode sharing and tie breaking use the same engine
  as the finite run. Arrival times are integer milliseconds; internal event times
  may be fractional. The tolerance for memory admission remains one byte.
- `inspect()` reports active requests, queue, pending arrivals, replica state,
  KV, waiting reason and rental accrued through the observed time. It does not
  claim hardware GPU utilization. Returned data are detached from engine state.
- `maintain(replicaId, newConfig)` stops admission to that replica, drains its
  active requests using their existing configuration, and applies the new config
  before further admission. Existing waiting/future requests must remain feasible
  on at least one eventual replica. An invalid change is rejected atomically.
- `addReplica(config)` adds capacity without accelerating work on existing
  replicas. Rental includes idle provisioned replicas; a maintenance config's
  new rate applies when the change becomes effective.
- `records()` returns admitted request records, including incomplete records
  with null completion fields. `finish()` drains known arrivals, does not invent
  more visitors, and returns the finite result. It is for tests/batch consumers,
  not a game play/pause or clock control. An idle session clock never rewinds.
- `save()` stores a versioned action journal and current observation time.
  Restore validates and replays the journal instead of trusting saved results.
  It preserves remaining work without serializing Infinity or internal closures.

Prototype bounds are explicit: 64 replicas, 256 active requests per replica,
10,000 requests over a live session, 30,000 journaled actions, and observed live
model time at most 1e9 ms. A limit throws before adding the rejected input;
requests are never silently dropped. Finite `simulate` retains its previous
workload/time behavior. History compaction for an unlimited game is not included.

## Game session controller

`playground/session.js` exports `GameSession` in browser and Node. It depends on
the root `SimCore` and `ScenarioCore`, not on duplicated GPU/model presets.

```js
const game = GameSession.create({settings, popularity: 2, world: 'server-room'});
game.advanceTo(modelTimeMs);
game.setPopularity(0);    // only future visitors change
const state = game.inspect();
game.setWorld('orbital'); // presentation only; no reset or recalculation
const resumed = GameSession.restore(JSON.parse(JSON.stringify(game.save())));
```

Creation represents opening the service, not installing an empty rack. The
construction UI and browser clock driver are separate later work. No time
control or full graphics are added by this module.

The working clock starts at08:00. The same monotonic model milliseconds drive
arrivals and service: 08–18 morning,18–23 peak,23–08 night. The calendar day
number changes at midnight, with no clearing of work; the phase sequence repeats
at08:00. A single future browser time-scale must apply to both clock and service.
No offline elapsed time or offline revenue is generated by this module.

Popularity is base new users per model minute. Teaching profile multipliers:
morning1×, peak10×, night0.5×. These hours and rates are explicit provisional
assumptions, not traffic observations. A fractional arrival accumulator carries
across rate/phase changes; observation frequency cannot affect generated users.

Default task: one user, one request. `profile:{kind:'openclaw'}` instead schedules
the existing six-call public trace from `ScenarioCore.demo`. Setting popularity
to zero preserves all calls of already started tasks, including future calls.
This is fixed-arrival replay, not DAG/closed-loop agent execution.

Game save schema is separate (`ai-startup-session/1`) and includes world, source
fraction, settings metadata and the core journal. Restore checks settings against
actual/pending engine configurations. It is not the calculator's scenario JSON
schema. No file or network I/O is performed by either pure module.

## Verification

```sh
node --test tests/*.test.js
```

`finite-compat.test.js`: captured pre-refactor events and results.
`live-core.test.js`: observation invariance, restore, maintenance, KV and costs.
`game-session.test.js`: repeated phases, arrival changes, theme invariance,
OpenClaw future calls, save/restore and explicit quota failures.

Game session inspection exposes target `settingsByReplica` and actual
`appliedSettingsByReplica`. During maintenance, actual hardware and memory
stay unchanged until active work drains. Saves validate both against core state.

## Live task changes

`GameSession.setProfile(profile)` changes only future visitors. Accepted calls,
including future OpenClaw calls and queued requests, retain their tokens.
`initialProfile` and `profileChanges` extend session saves without changing the
schema version; old fixed-profile files remain readable. Restore validates each
visitor against the profile in effect when that visitor was generated.

`previewPlacement(settings)` checks both the future task and all unfinished
accepted calls. Shrinking hardware cannot strand queued long requests after
switching back to a short task. This conservative game rule requires every copy
to fit one such request; it does not model specialized routing.
