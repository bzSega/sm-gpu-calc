# LLM GPU Dashboard — навык построения интерактивных дашбордов-калькуляторов

Методология и рецепт создания одностраничных интерактивных обучающих калькуляторов/дашбордов (эталон в этом репо: `simulation.html`, обзор и раскрытая GPU-стойка).

## Когда применять
Нужен визуальный интерактивный «песочный» дашборд: физика/расчёты + слайдеры + drill-down + deep links, HTML с соседними файлами ядра, работает офлайн и на любом статическом хостинге.

## Структура проекта
```
project/
├── simulation.html         # единый интерфейс с inline drill-down
├── distr/                  # самодостаточный дистрибутив (generic README, без привязки к домену)
│   ├── index.html          # главная страница = основной уровень
│   ├── simulation.html    # тот же интерфейс по существующему URL
│   ├── sim-core.js        # расчётное ядро
│   └── scenario-core.js   # профили и форматы
├── skills/llm-gpu-dashboard/SKILL.md   # этот навык
└── scripts/render-check.sh # обязательная проверка рендера
```

## Рецепт одной страницы

1. **Fixed stage + scale.** Внутренний размер фиксирован (например 1920×1080), реальный экран — CSS-переменная `--scale = min(innerWidth/W, innerHeight/H)` и `transform: translate(-50%,-50%) scale(var(--scale))`. Вёрстка не плывёт никогда.
2. **Три зоны сверху вниз:** заголовок с живыми цифрами из состояния → панель контролов (слайдеры/селекты, каждый с `<output>`) → визуализация → статусная строка + выводы. Статус всегда текстом: «что происходит» человекочитаемо, не только цветом.
3. **Состояние и один `update()`.** Вся отрисовка — из одной функции `update()`, читающей контролы; каждый `input` на контролах вызывает её. Никакой логики в обработчиках.
4. **Физика — константами наверху скрипта** (объекты `MODELS`, `GPUS`), с комментарием-дисклеймером: это сценарные допущения, не официальные спеки. Дисклеймер дублировать на экране.
5. **Drill-down — инлайном.** Детализация открывается оверлеем (`position:absolute; inset:0`) в том же файле с кнопкой возврата. Никаких переходов между файлами — ломаются, если файлы лежат в разных папках.
6. **Крошечные значения — текстом.** Если величина может быть суб-пиксельной (полоска невидима), дублируй её явной строкой «X ГБ из Y» рядом.
7. **Deep links.** Все контролы читаются из URL (`?model=...&users=...`), чтобы сценариями делиться. Тестовый параметр (`drill=1`) открывает оверлей — им проверяют детализацию скриншотом.
8. **Idle/пустые состояния — честные.** Невозможная конфигурация → отдельное состояние «размещение невозможно», а не «∞ кластеров» и не фиктивные плитки.

## Обязательный рендер-чек перед коммитом/отправкой

`node --check` НЕ ловит рантайм-ошибки (TDZ, удалённые переменные, порядок объявлений), а скриншот дефолтного состояния не ловит поломку вёрстки в других режимах.

```bash
bash scripts/render-check.sh <file.html> "?params" /tmp/check.png
```

Механика: локальный `python3 -m http.server` (file:// и localhost часто заблокированы политикой браузерных тулов) → headless Chrome `--headless=new --enable-logging=stderr --screenshot` → `grep -i Uncaught` лога → скриншот осмотреть глазами в 2–3 крайних режимах (минимум, максимум, invalid/drill).

Проверено этим чеком за один день: TDZ `$`, обращение к удалённой переменной, формула, в которой idle-кластеры «ускоряли» запросы в 10 раз, TTFT по одному запросу вместо батча, а также два чисто вёрсточных бага в drill-down, видимых только на скриншоте:

- контейнер оверлея оказался CSS-grid'ом на N колонок → блок стойки (position:relative, внутри absolute-карты) зажался в одну ячейку шириной 1/8; лечится явным `container.style.display='block'` перед вставкой HTML;
- позиционированная сноска (`position:absolute; bottom:…`) наехала на карты; заметно только на скриншоте — текст «работает» не значит «не перекрывается».

## Анти-паттерны
- «Синтаксис прошёл → работает»
- Ссылочный drill-down между файлами
- Один скриншот дефолтного состояния для интерактивной страницы
- Частные имена (домены, проектные коды) в дистрибутиве — distr должен быть готов к выкладке куда угодно априори
- Логика расчёта, размазанная по обработчикам событий

## Двухуровневая детализация (обзор ↔ drill-down)

Разделение уровней (вывод ревью 27.09.2026): **обзор = сценарий и результат, drill-down = устройство конкретного объекта и объяснения**.
- На обзоре: контролы сценария, плитки объектов с итоговым состоянием (загрузка/очередь), итоговый результат, компактные легенды.
- В drill-down: сводные ячейки по ключевым ресурсам объекта (например «доступно / занято / осталось / почему растёт»), разбивка на единицах (карта/узел), пояснения связей («X растёт с Y»), нумерация частей с объяснением «части одной модели, не копии».
- Анти-паттерн: захардкоженные константы в тексте («800 ГБ», «минимум 6 карт») — значения должны считаться из состояния.

## Верификация расчётов
Формулы (throughput, capacity, latency) прогонять через внешнее ревью — короткая изолированная задача «только ревью, файл не менять». Граничные кейсы обязательно: 1 пользователь, кластеров больше/меньше нужного, конфигурация «не влезает».
